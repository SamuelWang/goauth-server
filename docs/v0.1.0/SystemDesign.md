# System Analysis and Design Document - v0.1.0

## 1. System Analysis

### 1.1 Overview
"Goauth" is a web-based authentication and authorization service. It serves as a centralized identity provider, enabling users to sign in via social providers (initially Google) and allowing administrators to manage user sessions and client applications. It adheres to OAuth2 and OIDC standards.

### 1.2 Actors
*   **User:** An end-user who wishes to access client applications secured by Goauth. They perform actions like signing up, signing in, and managing their profile.
*   **Administrator:** A privileged user responsible for managing the system, including user accounts, client applications, and viewing audit logs.
*   **Client Application:** External applications (web, mobile, etc.) that delegate authentication to Goauth.
*   **OAuth Provider (Google):** The external identity provider used for authentication.

### 1.3 Functional Requirements
Based on the Software Requirements Specification (SRS) v0.1.0:

*   **Authentication:**
    *   **Sign In:** Users must be able to sign in using their Google account.
    *   **Sign Up:** New users signing in via Google must automatically have a user profile created.
    *   **Session Management:** Upon successful login, the system must issue a JWT access token via a secure cookie.
*   **Logging:**
    *   **Activity Logging:** Critical user activities (login, updates) must be logged for auditing purposes.

### 1.4 Non-Functional Requirements
*   **Security:**
    *   CSRF protection must be implemented.
    *   Secure storage of tokens and sensitive data.
    *   Use of HTTPS is assumed for production.
*   **Scalability:** The system uses a stateless architecture (REST API) facilitating horizontal scaling.
*   **Reliability:** Database integrity is enforced via PostgreSQL ACID properties.

## 2. System Design

### 2.1 Architecture
The project follows a **Clean/Layered Architecture** to separate concerns and ensure maintainability.

*   **Presentation Layer (CMD/API):** Handles HTTP requests, routing, and request validation. Implemented using **Gin Web Framework**.
    *   Location: `cmd/auth-service/`, `internal/app/auth-service/` (planned)
*   **Business Logic Layer (Service):** Contains the core business rules and use cases. It orchestrates data flow between the presentation and data access layers.
    *   Location: `internal/service/` (planned)
*   **Data Access Layer (Repository):** interacting with the database.
    *   Location: `internal/repository/` (generated by **sqlc**)
*   **Database:** PostgreSQL.

### 2.2 Technology Stack
*   **Language:** Go 1.25+
*   **Web Framework:** Gin (`github.com/gin-gonic/gin`)
*   **Database:** PostgreSQL 16+
*   **Database Tooling:**
    *   `sqlc` for type-safe Go code generation from SQL.
    *   `pgx` as the PostgreSQL driver.
    *   `golang-migrate` (implied or custom scripts) for schema migrations.
*   **Configuration:** `godotenv` for environment variable management.
*   **Authentication:** Google OAuth2 (using standard libraries or `golang.org/x/oauth2`).

### 2.3 Database Design

#### Schema Overview
The database uses PostgreSQL with the `pgcrypto` extension for UUID generation.

#### Tables

**1. `users`**
Stores user profile and authentication information.

| Column | Type | Constraints | Description |
| :--- | :--- | :--- | :--- |
| `id` | UUID | PK, Default: `gen_random_uuid()` | Unique identifier for the user. |
| `email` | Text | Unique, Not Null | User's email address. |
| `email_verified` | Boolean | Default: `false` | Whether the email has been verified. |
| `first_name` | Text | Nullable | User's first name. |
| `last_name` | Text | Nullable | User's last name. |
| `is_active` | Boolean | Default: `true` | Soft deletion/ban flag. |
| `locale` | Varchar(10) | Nullable | User's preferred locale (e.g., 'en-US'). |
| `provider` | Text | Nullable | OAuth provider name (e.g., 'google'). |
| `provider_id` | Text | Nullable | Unique ID from the provider. |
| `last_login_at` | Timestamp | Nullable | Timestamp of last successful login. |
| `created_at` | Timestamp | Default: `now()` | Record creation time. |
| `updated_at` | Timestamp | Default: `now()` | Record last update time. |

*Indexes:*
*   `users_email_key` on `email`
*   `users_provider_provider_id_key` on `(provider, provider_id)` for fast lookups during OAuth callbacks.

**2. `schema_migrations`**
Tracks the state of database migrations.

### 2.4 API Design
The API follows RESTful principles.

#### Authentication Endpoints
*   `GET /auth/google/login`: Initiates the Google OAuth flow.
*   `GET /auth/google/callback`: Handles the redirect from Google, verifies the code, creates/updates the user, and sets the session cookie.
*   `POST /api/v1/auth/logout`: Invalidates the session.

### 2.5 Security Design

#### OAuth Flow
1.  Client requests login by redirecting to `/auth/google/login`.
2.  Server redirects to Google Consent Screen.
3.  User approves.
4.  Google redirects back to `/auth/google/callback` with a code.
5.  Server exchanges code for ID Token and Access Token.
6.  Server verifies ID Token.
7.  Server checks if user exists in DB:
    *   **Exists:** Update `last_login_at`.
    *   **New:** Create new record in `users`.
8.  Server issues a JWT (Session Token) to the client via an `HttpOnly`, `Secure` cookie.

#### JWT Strategy
*   **Payload:** User ID, Email, Role (future scope).
*   **Signing:** ES256 (Elliptic Curve P-256).
*   **Expiration:** Short-lived (60 minutes) with a refresh mechanism (future scope).

#### CSRF Protection
*   For state-changing requests (POST, PUT, DELETE), the API will require a CSRF token or use the Double Submit Cookie pattern, or rely on `SameSite=Strict` cookie attributes for modern browser protection.
